# KNUS Service Desk — Telegram-бот приёма заявок

Бот: [@knus_marketing_bot](https://t.me/knus_marketing_bot)

Мультиотдельный приём заявок: заявитель выбирает **отдел-исполнитель** (маркетинг, ДИТ, …),
бот создаёт задачу в плане Microsoft Planner **этого** отдела и шлёт уведомление в **его** чат.
Отделы настраиваются в `departments.yaml` без правки кода. Диалог с кнопками, нормализация
описания через LLM (Qwen3 на OVMS), гибридное хранение файлов (чат + SharePoint), «Мои заявки»
со статусом. Long polling — вебхук и открытые порты не нужны.

## Структура

```
main.py              точка входа, сборка Application, long polling
departments.yaml     РЕЕСТР отделов-исполнителей (маршрутизация; правится без пересборки)
bot/config.py        чтение .env
bot/departments.py   загрузка/валидация реестра отделов (DepartmentRegistry)
bot/router.py        TicketRouter: по отделу → план/сегмент/чат/исполнители
bot/constants.py     справочники: подразделения-заявители, типы обращений, приоритеты
bot/handlers.py      ConversationHandler — вся машина состояний
bot/ticket.py        модель заявки, номер, форматирование текстов
bot/llm.py           нормализация описания (OpenAI-совместимый эндпоинт)
bot/graph.py         Microsoft Graph (мультиплановый): Planner + SharePoint
bot/db.py            SQLite: связь пользователь→заявки, агрегаты и статусный кеш
bot/api.py           HTTP API (aiohttp): /health, /api/stats, /api/tickets + рефрешер
bot/storage.py       jsonl-логи заявок и fallback
```

## Сценарий

`/start` → **главное меню**: «📝 Создать заявку» / «📋 Мои заявки».

Создание заявки: **отдел-исполнитель** → ваше подразделение → тип обращения (список зависит
от отдела) → описание → материалы → дедлайн (`ДД.ММ.ГГГГ` или «Без срока») → приоритет →
контакт → сводка → ✅ Отправить / ✏️ Исправить / ❌ Отмена. Если включён один отдел — шаг выбора
исполнителя пропускается автоматически.

На каждом шаге есть «⬅️ Назад» — возврат на предыдущий шаг без потери введённого (с первого шага
ведёт в меню). Один шаг рисуется одной функцией `show_*`, поэтому «вперёд» и «назад» показывают его
одинаково. «Исправить» на сводке открывает меню полей; в режиме правки «Назад» превращается
в «⬅️ К сводке» и любой изменённый шаг возвращает сразу к сводке.

`/cancel` сбрасывает диалог, `/start` открывает меню, `/my` — статус своих заявок.

## Отделы-исполнители (`departments.yaml`)

Куда уходит заявка — определяет **выбранный отдел-исполнитель**, а не .env. Отделы описаны
в `departments.yaml` в корне проекта. В контейнере файл смонтирован как `/app/departments.yaml`
(volume в `docker-compose.yml`), поэтому правится на хосте **без пересборки образа**.

**Поля отдела:** `name`, `enabled`, `planner_plan_id` (обязателен у включённого),
`planner_bucket_id` (пусто → поиск по имени), `planner_bucket_name`, `notification_chat_id`,
`assignees` (email-ы; пусто = общая очередь), `request_types` (какие типы показывать),
`bucket_status` (необязательный маппинг сегмент доски → статус для заявителя).

**Что заполнить руками для ДИТ** (в `departments.yaml`, секция `it:`):
- `notification_chat_id` — **обязательно**, иначе уведомления ДИТ никуда не пойдут (в логе будет
  предупреждение). Как узнать chat_id — см. ниже (`/myid`).
- `assignees` — по желанию: список email-ов саппорта ДИТ, задача в Planner назначится на них.
  Пусто = задача в общей очереди плана. Для назначения приложению нужно право **User.Read.All**
  (Application) + admin consent; если его нет — задача создастся без назначения, заявка не упадёт.

**Как применить изменения:** отредактировать `departments.yaml` на сервере и выполнить
`docker compose restart marketing-bot` (файл читается при старте, пересборка не нужна).

**Совместимость.** Пустые поля отдела `marketing` подхватываются из .env
(`planner_plan_id←PLANNER_PLAN_ID`, `notification_chat_id←MARKETING_CHAT_ID` и т.д.). Если файла
нет/он битый/нет включённых отделов — бот откатывается в режим одного отдела (маркетинг из .env),
текущий прод не ломается.

**Метки Planner** (цветные теги типов) применяются только к плану маркетинга — там они настроены
(`categoryDescriptions`). У ДИТ меток нет: задачи создаются без тегов, чтобы не вешать безымянные.

**Номер заявки** получает префикс по отделу: `MKT-…` для маркетинга, `IT-…` для ДИТ.

## Как получить MARKETING_CHAT_ID (и chat_id ДИТ)

Telegram API принимает для лички только **числовой** id — `@username` не сработает.

1. Запусти бота (локально или в контейнере).
2. Открой в Telegram [@knus_marketing_bot](https://t.me/knus_marketing_bot), нажми **Start**.
3. Отправь `/myid` — бот ответит `chat_id: 123456789`.
4. Подставь это число в `MARKETING_CHAT_ID` в `.env` и перезапусти бота.

Для группы: добавь бота в группу, отправь `/myid` там — id группы будет отрицательным
(например `-1001234567890`). Бот должен быть участником группы, иначе отправка упадёт.

## Локальная проверка (без Planner)

Режим, где заявка нигде не создаётся, а только пишется в jsonl:

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Linux: .venv/bin/pip

# в .env:
#   PLANNER_ENABLED=false
#   LLM_NORMALIZE=false   # если LLM-сервер недоступен с твоей машины
#   DATA_DIR=./data

.venv/Scripts/python main.py                    # Linux: .venv/bin/python main.py
```

Пройди диалог в Telegram — заявка ляжет в `./data/requests.jsonl` со статусом `local_only`,
уведомление всё равно уйдёт в `MARKETING_CHAT_ID` (с пометкой, что в Planner не сохранено).

С `PLANNER_ENABLED=true` заявки создаются в реальном плане — для тестов лучше `false`.

LLM и Planner недоступны с твоей машины? Ничего страшного: недоступный LLM просто пропускает
нормализацию, недоступный Planner — пишет заявку в `data/planner_fallback.jsonl` и говорит
пользователю «временно не сохранена».

## HTTP API (статистика для веб-панели)

Рядом с ботом в том же процессе и asyncio-loop поднимается лёгкий HTTP-сервер (aiohttp) на
`0.0.0.0:API_PORT` — для панели в галерее `ai.knus.edu.kz`. Наружу порт **не публикуется**
(`expose`, не `ports`): API доступен только контейнерам сети деплоя как `marketing-bot:8080`.
Бот и API работают одновременно, polling не прерывается.

Все эндпоинты, кроме `/health`, требуют заголовок `Authorization: Bearer <API_TOKEN>`.
Пустой `API_TOKEN` → всё, кроме `/health`, отвечает `401`.

### Эндпоинты

- `GET /health` → `{"status":"ok"}` — без токена, для healthcheck.
- `GET /api/stats` → сводка для плашек и графиков:
  `total`, `today`, `by_status {new,in_progress,done}`, `by_target [{name,count}]` (по
  отделам-исполнителям), `by_department [{name,count}]` (по подразделениям-заявителям),
  `by_type [{name,count}]`, `by_priority {urgent,normal,low}`,
  `by_day [{date,count}]` (30 дней, пропуски заполнены нулями), `avg_per_day`.
  Необязательный разрез: `?department_target=it` — статистика только по этому отделу.
- `GET /api/tickets` → список с фильтрами и пагинацией. Параметры (все необязательны):
  `target_department` (=`department_target`), `department`, `type`, `status`
  (new/in_progress/done), `priority` (urgent/normal/low), `date_from`, `date_to` (ГГГГ-ММ-ДД),
  `q` (поиск по сути, контакту и номеру), `page` (с 1), `per_page` (до 100). Ответ:
  `{total, page, per_page, items:[{id, created_at, target_department, department, request_type,
  task_type, summary, deadline, priority, status, contact, planner_task_id, planner_url,
  attachments_count, source, submitter_name, submitter_email}]}`. Сортировка — новые сверху.
- `POST /api/tickets` → **приём заявки с веб-портала** (KNUS Digital). `multipart/form-data`.
  Авторизация: `Authorization: Bearer <API_TOKEN>` + заголовки `X-KNUS-User-Email`
  (обязательно, домен `@knus.edu.kz`, иначе `403`) и `X-KNUS-User-Name` (URL-кодированный).
  Поля формы: `target_department` (код отдела, по умолчанию `marketing`), `department`
  (+`department_other`), `task_type` (+`task_type_other`; тип должен входить в типы отдела),
  `description` (10–5000), `deadline` (`ГГГГ-ММ-ДД`/`ДД.ММ.ГГГГ`/пусто), `priority`
  (urgent/normal/low), `contact`, файлы (до `MAX_ATTACHMENTS`, ≤20 МБ каждый). Создаёт задачу
  в плане отдела, грузит файлы в SharePoint, шлёт уведомление в чат отдела, пишет в SQLite
  (`source='web'`). Ответ `201 {ok, id, planner_url, attachments, warnings}` или `4xx/5xx`
  с `{error, message}`. Веб-заявки видны в `/api/tickets` и «не мои» в боте (это заявки портала).

### Как статус попадает в API

Статус в API — три состояния по `percentComplete` задачи Planner: `0 → new`, `1–99 → in_progress`,
`100 → done`. (Это отдельно от бота: в «Мои заявки» статус детальнее — по сегменту, шесть
состояний.) API **не** ходит в Planner на каждый запрос — это было бы медленно. Вместо этого
фоновая задача раз в `STATUS_REFRESH_SECONDS` (по умолчанию 90) группирует активные заявки
по планам отделов и обходит **каждый план одним** запросом, пересчитывает статусы и пишет
`status` + `status_updated_at` в SQLite. API отдаёт готовые значения из базы — быстро. Заявки
со статусом `done` из обхода выпадают. Если план недоступен — рефрешер пропускает его до
следующего цикла, а API отдаёт последний известный статус.

Таблица `requests` при старте мягко доливается колонками `status`, `status_updated_at`,
`attachments_count`, `contact` (через `PRAGMA table_info`, идемпотентно — старые строки целы,
`status` у них `new`).

## Состояние диалога переживает перезапуск

Шаг диалога и черновик заявки сохраняются на volume в `/data/ptb_state.pkl`
(`PicklePersistence`). Без этого при каждом передеплое (`docker compose up -d --build`)
состояние в памяти обнулялось, и у тех, кто не дозаполнил заявку, кнопки шагов
(департамент, тип, «Назад», «Отправить» и т.д.) переставали отвечать — они привязаны
к состоянию. Кнопки-точки входа («Создать заявку», «Мои заявки», `/start`) работали всегда,
поэтому со стороны выглядело как «часть кнопок не работает».

`bot_data` намеренно не сохраняется (там httpx-клиенты и asyncio-локи — не пиклятся).
Дополнительно любой устаревший callback (кнопка на старом сообщении вне текущего шага)
теперь отвечает всплывающим окном «Эта кнопка устарела, нажмите /start», а не молчит.

Если после аварийного завершения бот не стартует из-за битого `ptb_state.pkl` — удалите этот
файл (потеряются только незавершённые черновики, поданные заявки в SQLite/Planner не тронуты).

## Логи заявок

`./data` смонтирован в контейнер как `/data`:

- `requests.jsonl` — **каждая** отправленная заявка, независимо от Planner
  (`status`: `planner_ok` / `planner_failed` / `local_only`);
- `planner_fallback.jsonl` — только заявки, которые не удалось создать в Planner, с текстом ошибки.

## «Мои заявки»

Кнопка «📋 Мои заявки» на `/start` и команда `/my`. Список — inline-кнопки вида
`№MKT-… · Дизайн · краткая суть…`, по 8 на страницу с навигацией «⬅️/➡️». По нажатию бот
читает задачу из Planner **в момент просмотра** (не кеширует — маркетолог мог только что
подвинуть карточку). Кнопка «⬅️ К списку» возвращает обратно.

### Откуда берётся статус

Статус определяется **сегментом**, в котором лежит карточка — доска и есть поток работы:

| Сегмент | Статус для заявителя |
|---|---|
| 📥 Новые заявки | 🆕 Принята, ждёт очереди |
| ✅ Принято в работу | ✅ Принята в работу |
| 🎨 В производстве | 🎨 В работе |
| 👀 На согласовании | 👀 На согласовании |
| ⏸ Ожидает уточнений | ⏸ Нужны уточнения — с вами свяжутся |
| 🚀 Готово | ✅ Готово |

Отметка «Завершено» на карточке (`percentComplete=100`) перекрывает сегмент: её ставят, не
перетаскивая задачу. Если сегмент неизвестен (переименовали, добавили новый) — заявитель увидит
имя сегмента как есть; если и его нет — запасной путь по `percentComplete`
(`0` → 🆕 Новая, `1–99` → 🔧 В работе, `100` → ✅ Готово).

Почему не по `percentComplete`: он даёт всего три состояния, а доска — шесть, включая
«На согласовании» и «Нужны уточнения», которые в проценте не выражаются. Соответствие
«сегмент → статус» — в `BUCKET_STATUS` ([constants.py](bot/constants.py)); при переименовании
сегментов правь там. Имена сегментов кешируются на 5 минут, сам статус — никогда.

Раздел живёт вне `ConversationHandler`, поэтому `/my` работает и посреди заполнения заявки,
не сбивая её.

Если задачу удалили из плана или Graph ответил ошибкой — «❔ Статус недоступен — уточните
у отдела маркетинга». Заявка при этом остаётся в списке.

**Где хранится связь.** SQLite `/data/requests.db` (`REQUESTS_DB_PATH`) на том же volume, что
и jsonl-логи, — переживает `docker compose up --build`. Строка пишется при **успешном** создании
задачи в Planner: без `planner_task_id` статус читать неоткуда. Заявку отдаём только её автору —
`id` из `callback_data` проверяется вместе с `telegram_user_id`.

**Старые заявки не появятся.** База начинает наполняться с момента внедрения; заявки, поданные
раньше, в ней отсутствуют и в списке не показываются. Они никуда не делись — лежат в
`requests.jsonl` и в Planner.

## Материалы к заявке (гибридное хранение)

Один файл — два маршрута, и скачивается он **ровно один раз**:

1. **Чат маркетинга** — файл пересылается по `file_id` (`send_photo`/`send_document`/…).
   Скачивания нет вообще, байты через бота не идут, поэтому мгновенно.
2. **SharePoint + Planner** — файл скачивается один раз через `getFile` и загружается в библиотеку
   группы плана, а ссылка прикрепляется к задаче как reference. Временный файл удаляется сразу
   после загрузки.

Порядок в `_submit`: создать задачу → ответить заявителю → карточка и файлы в чат → загрузка
в SharePoint → однократная запись `details` (описание + ссылки). Заявитель и маркетинг не ждут
SharePoint, а `details` пишется один раз, когда результат загрузки уже известен.

**Где файлы:** библиотека группы плана → `Заявки маркетинга/<номер заявки>/<имя файла>`.
Материалы одной заявки лежат в своей папке. Одноимённые файлы не затирают друг друга
(`conflictBehavior=rename`). Файлы >4 МБ грузятся через upload session кусками по 3.2 МБ,
чтобы не держать всё в памяти.

**Большой файл (>20 МБ).** Bot API не отдаёт такие через `getFile`. Заявка не падает: файл
принимается, уходит в чат маркетинга по `file_id` (это работает при любом размере), а бот
предупреждает, что в общую папку файл не попадёт и его лучше прислать ссылкой. В задаче Planner
такой файл помечен «слишком большой для загрузки — только в чате маркетинга».

**Сбой SharePoint.** Задача в Planner создаётся, файлы в чате уже есть, а в описании появляется
«материалы в чате маркетинга (SharePoint недоступен)». Ошибка Graph пишется в лог; при 401/403
подсказка про `Sites.ReadWrite.All` + admin consent. В jsonl-логи попадают имена, типы, размеры
вложений и статус загрузки каждого.

## Устройство плана Planner

Сегменты (слева направо) — поток заявки:

`📥 Новые заявки` → `✅ Принято в работу` → `🎨 В производстве` → `👀 На согласовании` →
`⏸ Ожидает уточнений` → `🚀 Готово`

Бот кладёт заявки в `📥 Новые заявки` и сам проставляет метки: тип задачи (`🎨 Дизайн`,
`🎬 Видео`, `📱 Соцсети`, `🌐 Сайт`, `🖨 Полиграфия`, `🎪 Мероприятие`) и `🔴 Срочно` при высоком приоритете.
Тип «Другое» метки не получает. Соответствие «тип → метка» — в `TASK_TYPE_CATEGORY`
([constants.py](bot/constants.py)); если менять метки в Planner, правь и там.

## Про выбор bucket'а

Graph отдаёт bucket'ы **не** в том порядке, в котором они видны в интерфейсе Planner: первым
в ответе идёт «Завершено», и первая тестовая заявка улетела именно туда. Поэтому bucket
выбирается так, по убыванию приоритета:

1. `PLANNER_BUCKET_ID`, если задан (сейчас — «📥 Новые заявки»);
2. поиск по имени из `PLANNER_BUCKET_NAME`;
3. первый bucket плана — только как последний резерв, с `WARNING` в логе.
